# GitHub 글쓰기 하네스

AI가 이 저장소의 Issue를 바탕으로 개발하거나 Issue를 생성·수정하거나 Issue 코멘트를 작성하거나 PR을 생성할 때 적용한다. 개발 중 확인한 개발자의 의도와 판단 근거를 해당 Issue에 남긴다. im-not-ai의 의미 보존·근거 기반 국소 수정·원문 대조 원칙을 GitHub 글에 맞게 적용한다. 이미 자연스러운 문장은 그대로 둔다.

## 글의 기준

현재 흐름과 판단 근거를 보여 주되, 독자가 결정에 필요한 내용만 남긴다.

- 첫 문장에서 문제나 결정을 밝힌다. 현재 흐름은 문제를 이해하는 데 필요한 부분만 설명한다. `속도가 느리다`보다 어느 단계에서 얼마나 걸렸는지처럼 확인한 사실을 적는다.
- 수치에는 측정 시점·대상·출처를 붙인다. 관련 실행 로그, PR, 코드 파일은 해당 문장 가까이에 링크한다. 근거가 없다면 숫자나 원인을 추정해 채우지 않는다.
- 같은 사실을 문단·목록·그림에서 반복하지 않는다. 한 문단에는 한 가지 판단만 담고, 중복 배경과 수식어를 덜어낸다. 짧게 쓰더라도 선택 이유, 제약, 미확인 사항은 생략하지 않는다.
- 확인된 경험은 담백하게 적되, 작성자에게 없는 경험을 1인칭으로 꾸며내지 않는다.
- 새 Issue는 담백한 `-습니다`체를 기본으로 한다. 기존 Issue를 수정하거나 코멘트를 달 때는 원래 글과 대화의 말투를 유지한다.

## Mermaid 사용

- 흐름에 단계가 여러 개 있거나 분기·상태 변화·대안의 관계를 글보다 빨리 이해할 수 있다면 Mermaid를 우선한다. 배포·CI 흐름은 `flowchart`, 호출 순서는 `sequenceDiagram`, 상태 전이는 `stateDiagram-v2`를 검토한다.
- 그림에는 이번 판단에 필요한 노드와 관계만 넣는다. 확인하지 않은 동작을 그리지 않고, 기존 흐름과 바뀐 흐름이 섞이지 않게 표시한다.
- 그림 앞뒤의 설명은 핵심 결론 한두 문장으로 줄인다. 그림 속 문장을 본문에서 다시 열거하지 않는다. 한 문장으로 끝나는 내용에는 그림을 만들지 않는다.
- GitHub의 `mermaid` 코드 블록으로 작성하고, 렌더링 결과에서 흐름과 라벨을 확인한다. 렌더링을 확인하지 못했다면 문법을 단순하게 유지하고 검증하지 못했다고 밝힌다.

## 초안 작성 전

- 요청과 근거 자료를 먼저 확인한다. Issue 수정은 기존 본문을, 코멘트는 해당 Issue와 대화 맥락을, PR 생성은 실제 변경 사항과 연결할 Issue를 읽는다.
- 확인되지 않은 구현 내용, 테스트 결과, 일정, 원인, 합의 사항은 만들어 쓰지 않는다. 아직 확인하지 못한 내용은 그 상태를 분명히 적는다.
- 제목과 `type:*` 라벨은 [Git 규칙](git-convention.md)을 따른다. 변경 유형을 본문에 다시 묻는 항목은 만들지 않는다.

## 작업별 작성 기준

### Issue 생성

- [Issue 템플릿](../../.github/ISSUE_TEMPLATE/issue.md)의 `문제 상황`, `기대 상태 (TO BE)`, `참고 자료` 항목을 사용한다.
- `문제 상황`은 핵심 문제를 먼저 적고, 필요한 현재 동작과 실제 사례·근거만 붙인다. 여러 단계나 분기가 문제의 핵심이면 Mermaid로 흐름을 보여 준다.
- `기대 상태 (TO BE)`에는 완료 여부를 판단할 수 있는 상태를 쓴다. 여러 조건이면 짧은 체크리스트로 나눈다. 참고 자료가 없으면 해당 항목을 비워 둔다.

### Issue 수정

- 기존 본문과 요청한 변경 범위를 대조한다. 이미 기록된 요구사항, 결정, 링크를 임의로 지우거나 뜻을 바꾸지 않는다.
- 필요한 부분만 고치고, 현재 템플릿과 다른 형식이라는 이유만으로 기존 Issue 전체를 다시 쓰지 않는다.

### 개발 중 Issue 기록

- 구현 중 원인, 새 제약, 중요한 대안, 사용자 동작이나 완료 조건에 영향을 주는 선택이 확인되면 그때 Issue를 갱신한다. PR 작성 때까지 미루지 않는다. 단순한 코드 배치나 이름 선택은 기록하지 않는다.
- `문제 상황`에는 새로 확인한 사실과 근거, 중요한 대안과 선택 이유를 짧게 잇는다. 선택지가 서로 다른 흐름을 만들면 Mermaid로 차이를 보여 준다. `기대 상태 (TO BE)`에는 결정으로 바뀐 동작·범위·제약을 반영한다. 자료가 있으면 `참고 자료`에 연결한다. 새 고정 항목을 만들거나 기존 내용을 덮어쓰지 않는다.
- 결정의 근거가 대화 중에 형성되거나 경과를 남겨야 하면 Issue 코멘트에 관찰 → 고려한 대안 → 선택과 이유 → 남은 불확실성을 짧게 남긴다. 본문은 현재 합의된 상태, 코멘트는 그 상태에 이른 경과를 담당한다.
- 개발자의 의도나 선택 이유를 코드만 보고 알 수 없다면 추정해 쓰지 않는다. 확인 가능한 사실과 열린 질문을 Issue 코멘트에 남기고 개발자에게 이유를 묻는다. 답을 받기 전에는 선택을 확정된 결정처럼 본문에 쓰지 않는다. 그 선택이 동작이나 완료 조건을 좌우한다면 확인 전까지 해당 구현과 PR 완료 판단을 보류한다.
- 원래 Issue의 완료 조건과 별개로 진행할 수 있는 작업을 발견하면 별도 Issue를 만들고 원래 Issue와 서로 연결한다. 새 Issue에는 발견한 배경, 분리한 이유, 남은 작업과 완료 조건을 간단히 옮긴다. 원래 Issue에도 분리 사실과 링크를 남긴다. 현재 작업의 범위를 조용히 넓히거나 PR 설명에만 후속 작업을 남기지 않는다.
- PR을 만들기 전에 Issue 본문과 코멘트를 읽어 이번 변경을 낳은 중요한 판단이 남아 있는지 확인한다. 빠져 있으면 근거를 확인해 Issue에 기록한 뒤 PR에는 실제 변경만 요약한다.

### Issue 코멘트 작성

- 질문에는 답을, 진행 상황에는 바뀐 점을 먼저 쓴다. 코멘트마다 같은 형식을 강요하지 않는다.
- 확인 방법이나 결과를 보고할 때는 실제 실행한 명령·환경·결과를 적는다. 실행하지 않은 검증은 실행 예정 또는 미확인으로 구분하고, 실패·제약도 숨기지 않는다.
- 본문에는 완료를 판단할 조건을, 코멘트에는 실제 확인 명령·환경·결과를 남긴다. 결과를 기록하려고 본문에 확인 방법·결과 항목을 새로 만들지 않는다.

### PR 생성

- [PR 템플릿](../../.github/pull_request_template.md)의 `관련 Issue`, `변경 내용` 항목을 사용한다. 연결할 Issue 번호를 확인하고, 병합 시 닫을 Issue일 때만 `Closes #번호`를 쓴다.
- 변경 내용에는 실제 diff에서 확인한 핵심 변경과 이유만 쓴다. 흐름이 달라져 글로 설명하기 길어지면 Mermaid로 전후 관계를 보여 준다.
- 작업 브랜치에서 `dev-*`로 내는 PR 제목에는 Issue ID를 넣는다. `release-*`에서 `main`으로 내는 PR은 버전을 표시한다. 해당 `type:*` 라벨도 지정한다. 자세한 규칙은 [Git 규칙](git-convention.md)을 따른다.

## 윤문 순서

1. **진단:** 초안을 한 번 읽고 실제로 어색한 구절만 찾는다. 번역투, 내용 없는 평가, 기계적 열거, 접속사·종결어미의 밀집을 살핀다. 패턴이 있다는 이유만으로 모든 문장을 고치지 않는다.
2. **국소 수정:** 어색한 구절만 아래 기준으로 바꾼다. 문단 전체를 다시 써야 한다면 사실이나 인과관계가 바뀌지 않았는지 문장마다 확인한다. 윤문하면서 새 주장, 비유, 결론을 넣지 않는다.
3. **원문 대조:** 원문·요청·근거 자료와 수정본을 나란히 본다. 사실, 수치, 날짜, 코드·명령·경로, Issue 번호, 링크, 직접 인용과 핵심 기술 용어를 보존한다. 증상과 원인 주장도 실제 코드·로그와 대조한다. 자료가 주장을 뒷받침하지 않으면 원인으로 단정하지 않는다. `~로 보인다`를 `~이다`로, `~해야 한다`를 `~한다`로 바꾸지 않는다. 비교가 어려우면 해당 수정을 되돌린다.
4. **게시 전 확인:** 필요한 템플릿 항목과 링크가 있고, 빈 안내 문구나 `Closes #` 같은 미완성 표시가 없는지 확인한다. Issue 수정에서는 요청하지 않은 기존 내용을 잃지 않았는지 다시 확인한다. 마지막으로 중복 설명을 덜고 Mermaid가 사실·문장과 일치하는지 확인한다.

## 게시 전 독립 평가

Issue 생성·본문 수정·코멘트 작성과 PR 생성의 초안이 GitHub에 올라가기 전에 하위 에이전트 한 명에게 읽기 전용 평가를 맡긴다. 초안과 함께 요청, 기존 Issue의 관련 문맥, 확인한 코드·로그·diff를 전달한다. 평가자는 GitHub에 쓰거나 파일을 고치지 않는다.

평가자는 근거 없는 사실·수치·원인, 개발자 의도와 다른 결정, Issue에 빠진 중요한 선택, 불필요한 설명, Mermaid의 정확성과 필요성, 템플릿·링크 오류만 짚는다. 문제가 없으면 통과라고 답하고, 문제가 있으면 근거가 있는 수정 사항만 짧게 제시한다. 주 작업 에이전트는 지적을 자료와 대조해 초안을 고친 뒤 게시한다. 사실이나 결정이 바뀐 경우에는 한 번 더 평가받는다.

하위 에이전트를 사용할 수 없으면 초안을 보관하고 평가가 불가능한 이유를 알린다. 평가 없이 게시한 것으로 처리하지 않는다.

### 자주 고칠 표현

아래는 치환 목록이 아니라 진단 예시다. 문맥에서 자연스럽거나 의미가 달라질 경우 원문을 유지한다.

| 발견한 구절 | 고치는 방향 |
| --- | --- |
| `~를 통해`, `~에 있어서`, `~와 관련하여`가 반복됨 | 행위와 대상을 직접 쓴다. `로그를 통해 확인했다`는 `로그에서 확인했다`로 줄일 수 있다. |
| `~에 의해 생성되었다`, `~되어진다` | 행위자가 확인되면 주어로 쓰고, 이중 피동은 단순 피동으로 고친다. |
| `결론적으로`, `시사하는 바가 크다`, `혁신적인` | 내용 없는 평가는 덜고 관찰한 사실이나 결정을 바로 쓴다. |
| `문제는 ~라는 점이다`, `~하는 이유다`가 반복됨 | 실제 문제나 원인을 주어와 동사로 직접 쓴다. 새 결론 문구를 덧붙이지 않는다. |
| `먼저·다음으로·마지막으로`와 불릿이 계속 나옴 | 순서가 중요할 때만 목록을 남기고, 설명은 문단으로 잇는다. |
| `또한`, `따라서`, 같은 종결어미가 한 문단에 몰림 | 논리 연결을 남기면서 중복되는 표현만 덜어낸다. 문장 길이를 일부러 맞추지 않는다. |
| 영어 표기와 괄호 설명이 매번 반복됨 | 첫 등장만 설명한다. API·CI·CD·Gradle 같은 팀의 기술 용어는 그대로 둔다. |

수치나 링크를 추가하는 일은 윤문이 아니라 사실 보강이다. 근거를 확인한 뒤에만 추가한다. 확인하지 못한 내용은 그럴듯한 문장으로 메우지 않는다.
