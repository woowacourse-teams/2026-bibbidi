# Frontend Agent Convention

이 문서는 비비디 FE 기능을 개발할 때 Agent가 따라야 하는 팀 규칙을 정의한다.

코드 포맷과 기계적으로 검사할 수 있는 작성 규칙은 ESLint와 Prettier가 담당한다. 이 문서는 자동화하기 어려운 작업 방식, 설계 기준, 변경 범위와 완료 조건을 다룬다.

이 문서에 없는 규칙을 임의로 만들지 않고 기존 코드와 주변 문맥을 따른다.

## 작업 원칙

1. 구현 전에 Notion Task와 인수조건을 끝까지 확인한다.
2. Git 작업 방식은 [Git Convention](./git-convention.md)을 따른다.
3. Task 요구사항과 이 문서가 충돌하면 구현 전에 질문한다.
4. 요구사항이 여러 의미로 해석될 수 있으면 임의로 결정하지 않는다.
5. Task와 관계없는 파일을 수정하거나 일괄 포맷하지 않는다.
6. 새로운 라이브러리를 추가할 때는 필요성과 기존 대안을 먼저 확인한다.
7. 기존 코드로 해결할 수 있는 기능을 중복 구현하지 않는다.
8. 구현 후 이 문서의 완료 조건을 기준으로 검증한다.

## 작업 시작 전 확인사항

Agent는 구현 전에 다음 항목을 확인한다.

- Notion Task ID와 URL
- 변경 유형과 대상 Trunk
- 인수조건
- 제외 범위
- 관련 디자인
- 관련 API 계약
- 기존 구현과 재사용 가능한 코드
- 실행해야 할 검증 명령

FE 작업 브랜치는 `release-fe`를 기준으로 생성한다.
하나의 Notion Task는 하나의 작업 브랜치와 하나의 PR로 진행한다.

```text
release-fe
└─ {prefix}/{task-id}
```

브랜치 이름과 PR 규칙은 Git Convention을 따른다.

## 변경 범위

- 하나의 Task에는 하나의 목적만 포함한다.
- 인수조건을 만족하는 데 필요한 최소 범위만 수정한다.
- 기능 구현과 관계없는 리팩터링을 함께 진행하지 않는다.
- 기존 코드의 구조 개선이 필요하면 현재 Task에 필수인지 먼저 판단한다.
- 필수가 아닌 리팩터링은 별도 Task로 분리한다.
- 자동 포맷으로 기존 파일이 대량 변경되지 않도록 확인한다.
- Lockfile 변경은 패키지 변경이 있는 Task에만 포함한다.

## 의존 방향

기본 의존 방향은 다음과 같다.

```text
Page
  → Feature
    → Component / Hook
      → API Client / Utility
```

- Page는 화면을 구성하고 Feature를 조합한다.
- Feature는 하나의 사용자 행동과 관련된 상태 및 흐름을 관리한다.
- Component는 화면 표현과 사용자 입력을 담당한다.
- Hook은 재사용 가능한 React 상태와 생명주기 로직을 담당한다.
- API Client는 HTTP 요청과 응답 처리를 담당한다.
- Utility는 React에 의존하지 않는 순수 로직을 담당한다.

하위 계층이 상위 계층을 참조하지 않는다.

```text
허용

Page → Feature
Feature → Component
Feature → Hook
Feature → API Client
Component → API Client
Component → Utility
Hook → API Client
Hook → Utility

금지

Component → Page
Shared Component → Feature
Utility → React Component
```

Component와 Hook은 API Client와 Utility를 참조할 수 있다. 실제 HTTP 요청은 API Client에서만 수행한다.

재사용 가능성을 예상해서 코드를 성급하게 공통화하지 않는다. 두 곳 이상에서 실제로 같은 책임으로 사용되고 변경 이유도 같을 때 공통화를 검토한다.

## React 컴포넌트

- 컴포넌트는 화면 표현과 사용자 상호작용에 집중한다.
- JSX 내부에 복잡한 도메인 규칙을 직접 작성하지 않는다.
- 컴포넌트가 데이터 조회, 변환, 화면 표시를 모두 담당하지 않도록 분리한다.
- Props는 컴포넌트가 실제로 필요한 최소 데이터만 전달한다.
- Props drilling이 불편하다는 이유만으로 전역 상태를 추가하지 않는다.
- 렌더링 최적화 도구를 근거 없이 사용하지 않는다.
- `useMemo`, `useCallback`, `memo`는 측정되거나 명확한 필요가 있을 때 사용한다.
- Fragment보다 의미에 맞는 시맨틱 요소를 우선한다.

## 상태 관리

상태는 사용하는 곳과 가장 가까운 위치에 둔다.

```text
한 컴포넌트에서만 사용
→ 컴포넌트 로컬 상태

하나의 Feature에서 공유
→ Feature Hook 또는 Feature 상태

여러 화면에서 공유
→ 전역 상태 검토

서버에서 가져온 데이터
→ 서버 상태 관리 계층
```

- 로컬 상태와 서버 상태를 구분한다.
- 서버 응답을 불필요하게 전역 상태에 복사하지 않는다.
- 파생 가능한 값은 별도 상태로 저장하지 않는다.
- 상태 관리 라이브러리를 Task 범위 밖에서 임의로 추가하지 않는다.
- 새 전역 상태가 필요하면 사용 범위와 수명, 대안을 먼저 설명한다.

## API 통신

- React 컴포넌트에서 직접 `fetch`를 호출하지 않는다.
- HTTP 요청은 API Client 또는 합의된 데이터 접근 계층에서 수행한다.
- API URL을 컴포넌트에 하드코딩하지 않는다.
- Request와 Response 타입은 API 계약을 기준으로 작성한다.
- API 응답 타입과 화면에서 사용하는 모델이 다르면 변환 경계를 둔다.
- 날짜, nullable, optional 필드는 API 계약과 일치하는지 확인한다.
- 인증이 필요한 요청과 공개 요청을 구분한다.
- 오류 응답을 화면마다 임의로 해석하지 않는다.
- 존재하지 않는 API나 응답 필드를 추측해서 사용하지 않는다.

API 계약이 확정되지 않은 경우 구현 전에 질문하거나 Mock 경계를 정의한다.

## 로딩·오류·빈 상태

데이터를 사용하는 화면은 필요한 상태를 함께 고려한다.

```text
초기 로딩
성공
빈 상태
오류
재시도
권한 없음
```

- 로딩 중임을 사용자에게 알린다.
- 데이터가 없는 상태와 오류 상태를 구분한다.
- 사용자가 복구할 수 있는 오류에는 재시도 방법을 제공한다.
- 내부 오류 메시지와 서버 응답 원문을 사용자에게 그대로 노출하지 않는다.
- 오류 응답은 [Error Handling](./error-handling.md)에 정의된 `id`, `status`, `message`를 기본 필드로 사용하고, 검증 실패 시 `errors` 배열을 처리한다.
- 오류·권한·재시도 UI는 오류 `id`로 처리 흐름을 분기하고 공개 `message`를 표시한다.
- 낙관적 업데이트를 사용하면 실패 시 복구 방법을 함께 구현한다.

## 스타일과 디자인 시스템

- UI Task는 구현 전에 Task에 지정된 디자인 원본과 관련 컴포넌트를 확인한다.
- 디자인에 없는 상태나 동작이 필요하면 임의로 만들지 않고 질문한다.
- 디자인과 인수조건이 충돌하면 인수조건을 우선하되 충돌 내용을 공유한다.
- 같은 색상, 간격, 타이포 값을 여러 컴포넌트에 반복하지 않는다.
- 기존 공통 컴포넌트가 있으면 새로 만들기 전에 재사용 가능성을 확인한다.
- 디자인 시스템 컴포넌트의 스타일을 화면에서 임의로 덮어쓰지 않는다.
- Task와 관계없는 전역 스타일을 변경하지 않는다.
- 반응형 동작이 필요한 화면은 최소 지원 너비와 레이아웃 변화를 확인한다.
- 시각적 유사성뿐 아니라 상호작용 상태도 확인한다.

필요한 상태가 디자인에 없다면 다음을 먼저 확인한다.

- Hover
- Focus
- Pressed
- Disabled
- Loading
- Error
- Empty

## 접근성

- 클릭 동작에는 의미에 맞는 `button` 또는 `a` 요소를 사용한다.
- `div`에 클릭 이벤트만 추가하지 않는다.
- 입력 요소에는 접근 가능한 Label을 제공한다.
- 이미지에는 목적에 맞는 대체 텍스트를 제공한다.
- 장식용 이미지는 스크린 리더에서 제외한다.
- 키보드만으로 주요 동작을 수행할 수 있어야 한다.
- Focus 상태를 제거하지 않는다.
- 색상만으로 상태를 구분하지 않는다.
- Dialog와 Modal은 Focus 이동과 닫기 동작을 고려한다.

## 자동 코드 품질 검사

코드 포맷과 정적으로 검사 가능한 작성 규칙은 FE의 ESLint와 Prettier 설정을 따른다.
파일명, Import 정렬, TypeScript 세부 규칙, React 컴포넌트 선언 방식 등 자동화할 수 있는 코드 스타일은 이 문서에 중복해서 정의하지 않는다.
검사 도구가 구성된 이후에는 `FE/package.json`에 정의된 명령으로 검증한다.

ESLint 또는 Prettier 규칙 변경이 현재 Task의 목적이 아니라면 설정 파일을 수정하지 않는다. 규칙 변경이 필요하면 별도의 팀 합의를 거친다.

## 테스트

- 인수조건과 사용자 행동을 기준으로 테스트한다.
- 구현 세부사항보다 사용자에게 보이는 결과를 검증한다.
- 하나의 규칙을 여러 테스트 계층에서 중복 검증하지 않는다.
- 순수한 도메인 계산은 React와 분리해 작은 단위 테스트로 검증한다.
- 컴포넌트 테스트는 렌더링 결과와 사용자 상호작용을 검증한다.
- 외부 API는 실제 호출하지 않고 API 경계에서 대체한다.
- API 경계 테스트는 HTTP 요청·응답, 입력값 검증, 오류 응답 계약과 오류 변환을 검증한다.
- 테스트를 통과시키기 위해 제품 코드를 테스트 전용 구조로 변경하지 않는다.
- Snapshot 테스트를 기본 선택으로 사용하지 않는다.
- 버그 수정 시 가능한 경우 동일한 문제가 재발하지 않도록 테스트를 추가한다.

테스트 환경이 구성된 이후에는 관련 테스트를 반드시 실행한다.

## 패키지와 설정 변경

- 패키지를 추가하기 전에 기존 의존성으로 해결할 수 있는지 확인한다.
- 패키지의 목적과 사용 위치를 설명할 수 있어야 한다.
- 전역 설치에 의존하지 않는다.
- 프로젝트의 패키지 관리자인 pnpm만 사용한다.
- `package-lock.json`과 `yarn.lock`을 생성하지 않는다.
- 의존성 변경 시 `pnpm-lock.yaml`을 함께 갱신한다.
- Node와 pnpm 버전은 저장소에 정의된 범위를 따른다.
- 설정 파일 변경은 영향을 받는 실행 명령과 함께 검증한다.

## 완료 조건

Agent는 작업 완료 전에 다음 항목을 확인한다.

- [ ] Notion Task의 인수조건을 모두 충족했다.
- [ ] 제외 범위의 기능을 구현하지 않았다.
- [ ] Task와 관계없는 파일을 수정하지 않았다.
- [ ] 구성된 경우 ESLint 검사를 통과했다.
- [ ] 구성된 경우 Prettier 검사를 통과했다.
- [ ] TypeScript typecheck를 통과했다.
- [ ] Production build를 통과했다.
- [ ] 테스트 환경이 구성된 경우 관련 테스트를 통과했다.
- [ ] 로딩·오류·빈 상태를 확인했다.
- [ ] 기본 키보드 접근성과 시맨틱 구조를 확인했다.
- [ ] 새 패키지를 추가했다면 필요성과 영향을 설명했다.
- [ ] Lockfile 변경이 의존성 변경과 일치한다.
- [ ] 인수조건과 실제 구현이 일치한다.
- [ ] PR에서 사람이 판단해야 할 설계 선택과 영향 범위를 정리했다.
