# 백엔드 팀 하네스

작성자가 달라도 요구사항과 합의한 품질 기준을 일관되게 확인하기 위한 개발 절차다.
이 PR은 팀 검토를 위한 도입 초안이다. 병합 후 백엔드 작업에 적용하고 첫 5~10개 PR에서 비용과 효과를 확인한다.

## 기준과 적용 범위

- 기존 [코드 컨벤션](../convention/code-convention.md), [테스트 전략](../convention/test-strategy.md), [Git 컨벤션](../convention/git-convention.md)을 먼저 따른다.
- 추가 확인 항목은 [품질 기준](quality-standard.md), 참고할 구현은 [코드 예시](examples.md)에 둔다.
- 요구사항과 컨벤션이 충돌하면 충돌 지점과 대안을 작성자에게 확인한다. 코드에 우연히 남은 패턴을 새 규칙으로 만들지 않는다.
- 작은 버그 수정·문서 작업은 관련 항목만 적용하고 해당하지 않는 항목은 생략한다.

## 개발 시작

1. 작업의 Notion Task와 [요구사항 양식](task-template.md)을 확인한다. 기존 Task에 내용이 있으면 중복 작성하지 않는다.
2. 사람이 목적·기대 동작·예외·완료 조건을 정한다. 미결정 정책을 AI가 임의로 채우지 않는다.
3. AI는 관련 코드와 예시를 읽고 구현 전에 아래 내용을 짧게 제시한다.
   - 변경할 동작과 책임을 맡는 객체
   - 새 의존 관계 또는 기존 책임 변경과 그 이유
   - 확인이 필요한 정책과 검증할 조건
4. 이미 합의한 범위는 계속 진행한다. 미결정 정책에 의존하는 구현은 답을 받은 뒤 진행한다.

## 구현과 완료 확인

- 서비스에서 실행 순서를 읽을 수 있게 하고, 상태 변경 규칙은 책임을 가진 객체에 둔다.
- 새 클래스·계층·추상화가 필요하면 현재 요구사항에서 해결하는 문제를 설명한다.
- 최종 diff를 기준으로 요구사항 누락, 중복 규칙, 의존 관계, 기존 동작의 영향을 확인한다.
- 테스트는 변경 위험에 맞게 선택한다. 백엔드 전체 테스트 명령은 `cd BE && ./gradlew test`다.
- 실행한 명령과 결과, 실행하지 못한 검증과 이유를 구분한다. 테스트 통과만으로 요구사항 충족이나 운영 환경 검증을 주장하지 않는다.
- AI가 제안한 구현과 테스트도 사람이 핵심 조건과 경계 사례를 확인한다.

## PR과 재리뷰

- [PR 양식](../../.github/pull_request_template.md)에 요구사항, 주요 책임·선택 이유, 기존 동작 영향, 실제 검증 결과를 정리한다.
- 코드에서 알 수 없는 의도를 추측해 본문에 쓰지 않는다. 작성자가 결정 이유를 확인한다.
- 자동 리뷰는 [품질 기준](quality-standard.md)에 따라 근거와 위치를 제시한다. 설계 제안과 명시적 위반을 구분한다.
- 리뷰 반영 시 마지막 리뷰 이후 커밋 범위를 명시하고, 반영 내용·추가 영향·재검증 결과를 작성한다. 기준 커밋을 모르면 추측하지 않고 확인한다.
- 구조가 바뀌면 본문도 최종 코드에 맞게 고친다. 이전 설명에 댓글만 덧붙이지 않는다.

## 도구 연결과 강제 범위

- 저장소 루트와 BE의 AGENTS.md는 이 문서로 안내한다. 사용하는 도구가 해당 지침을 읽는지 팀원이 첫 작업에서 확인한다.
- 자동 로딩을 지원하지 않는 도구는 프로젝트 지침에 이 문서 경로를 연결하거나 작업 시작 시 읽도록 지정한다. 규칙 본문은 복제하지 않는다.
- PR 양식이 자동 입력되지 않으면 저장소의 양식을 직접 사용한다. 기본 브랜치 main과 작업 대상 release-be의 반영 시점이 다를 수 있다.
- 기존 자동 리뷰 설정에도 품질 기준을 연결한다. Draft PR은 현재 설정상 자동 리뷰 대상이 아니다.
- 기존 백엔드 CI는 BE 코드 변경 PR에서 테스트를 실행한다. 이 문서는 AI의 준수나 머지 차단을 기술적으로 보장하지 않는다.
- 필수 검사·승인 설정과 의존 관계 자동 검사는 팀 합의 후 별도 적용한다. 가독성·설계 선호를 AI 점수로 머지 차단하지 않는다.

## 첫 적용 기록

티뉴·라티·보예 모두 같은 절차를 사용한다. 개인 평가 대신 반복되는 재작업을 줄이는지 확인한다.
PR마다 아래 항목을 선택적으로 기록하고, 측정이 없으면 추정값을 채우지 않는다.

| 항목 | 기록 기준 |
| --- | --- |
| 최초 리뷰 시간 / 재리뷰 시간 | 실제 읽고 판단한 분, AI로 의도를 확인한 시간 포함, 대기 제외 |
| 책임·의존 관계 재작업 여부 | 합의 기준 때문에 구조를 다시 바꿨는지와 관련 리뷰 링크, 취향 제안 제외 |
| 작성자 준비·검증 시간 | 요구사항 정리와 하네스 확인에 쓴 실제 분 |
| 머지 후 결함 | 확인 기간과 해당 변경에서 발생한 결함 링크 |

도입 전후의 비슷한 크기·종류 PR을 비교하고 같은 리뷰어의 중앙값과 개별 값을 함께 본다.
기존 PR의 측정값이 없다면 감소율을 주장하지 않고 도입 후 기준선부터 수집한다.
