# 백엔드 품질 기준

아래 기준은 현재 일정·체크리스트 구현에서 추출한 검토 기준이다. 전체 기존 구현을 정답으로 취급하지 않는다.
기존 컨벤션과 충돌하면 컨벤션을 임의로 덮어쓰지 않고 팀에 확인한다.

## 1. 실행 순서가 보이는 서비스

- 서비스는 조회, 권한 확인, 도메인 동작, 저장, 다른 기능 호출을 연결한다.
- 주요 단계가 모호한 process/handle 이름 뒤에 숨지 않게 한다.
- 메서드 줄 수나 private 메서드 개수를 품질 기준으로 삼지 않는다.

## 2. 상태와 규칙의 책임

- 객체의 상태로 판단할 수 있는 업무 규칙은 해당 객체에 둔다.
- 호출자가 필드를 꺼내 같은 규칙을 반복하는지 확인한다.
- 외부 데이터 조회나 여러 기능의 실행 조정까지 무조건 도메인에 옮기지 않는다.

## 3. 설명할 수 있는 의존 관계

- 다른 도메인의 규칙을 호출자가 재구현하지 않고 제공된 동작을 사용한다.
- 새 의존성은 요청할 책임과 이유를 설명한다. 기존 호출 관계도 새 요구사항에 맞는지 확인한다.
- 주입 필드 개수를 줄이기 위한 책임 없는 클래스 분리나 미래 확장을 위한 추상화를 요구하지 않는다.
- 현재 AppointmentService → ChecklistService → ChecklistAppointmentService 구조 전체를 고정 규칙으로 만들지 않는다.

## 4. 이름과 실제 동작의 일치

- 호출자가 알아야 할 상태 변경, 대상 조건, 부수 효과를 이름이나 명시적인 계약으로 드러낸다.
- 모든 조건을 긴 이름에 나열할 필요는 없다. 조회처럼 보이지만 변경하거나, 전체처럼 보이지만 일부만 처리하는 오해를 찾는다.

## 5. 요구사항에 연결된 검증

- 정상 흐름과 실제 위험이 있는 권한·변경 제한·경계 조건을 검증한다.
- 함께 변경되어야 하는 데이터는 필요할 때 실패 시 롤백도 확인한다.
- 모든 기능에 동시성·통합 테스트를 요구하지 않고 테스트 전략에 따라 범위를 선택한다.

## 6. 최종 코드와 일치하는 PR

- 요구사항, 핵심 책임, 기존 동작의 영향과 실제 검증 결과가 드러나야 한다.
- 리뷰 중 구조가 바뀌면 없어진 클래스·흐름 설명도 수정한다.
- 작성자의 의도를 코드만 보고 만들어내지 않는다. 미확인 내용은 질문으로 남긴다.

## 리뷰 결과 구분

- **위반**: 명시된 요구사항·합의 규칙과 충돌한다. 근거 문서, 코드 위치, 발생하는 문제를 제시한다.
- **설계 제안**: 책임 이동·분리·명명에 다른 선택이 가능하다. 구체적인 읽기 비용이나 변경 위험을 설명하고 사람이 판단한다.
- **확인 필요**: 요구사항이나 의도를 확인할 수 없다. 부족한 정보를 묻고 오류로 단정하지 않는다.

“객체지향적이지 않다”, “깔끔하지 않다”만으로 수정을 요구하지 않는다.
예: “같은 변경 제한을 서비스와 도메인에서 각각 판단하므로 정책 변경 시 불일치할 수 있다”처럼 설명한다.
