# Issue·PR 작성 하네스

GitHub Issue를 생성·수정하거나 코멘트할 때, 또는 PR을 생성할 때 사용한다. `im-not-ai`의 [의미 보존과 필요한 구간만 고치는 방식](https://github.com/epoko77-ai/im-not-ai)을 참고하되, 이 저장소의 Issue·PR 문맥에 맞게 적용한다.

## 공통

1. 작성 전 관련 Issue, PR, 코드, 실행 기록을 확인한다. 확인하지 않은 원인·효과·수치를 단정하지 않는다.
2. 초안에서 번역투, 기계적인 병렬 나열, 추상적인 명사구, 같은 접속사·종결의 반복을 찾는다. 해당 구간만 자연스러운 한국어로 고친다. 이미 명확한 문장은 유지한다.
3. 원문의 사실, 수치, 날짜, 고유명사, 링크, 판단의 확신 정도를 보존한다. 불확실한 내용은 불확실하다고 적고, 검증 결과를 만들어 내지 않는다.
4. 게시 전 원문과 결과를 대조해 빠진 사실과 추가된 주장이 없는지 확인한다. 제목과 본문은 짧고 구체적으로 쓴다.

## 작성 위치별 적용

- **Issue 생성:** [Issue 템플릿](../../../.github/ISSUE_TEMPLATE.md)의 세 항목을 채운다. 문제의 이유와 완료 후 상태를 구분한다.
- **Issue 수정:** 기존 작성자의 의도와 결정, 체크 상태를 유지한다. 요청받은 부분을 중심으로 고치고 새 사실을 넣을 때는 근거를 확인한다.
- **Issue 코멘트:** 확인 방법(실행 명령·환경·대상)과 확인 결과(성공·실패·미확인, 관찰한 수치)를 적는다. 수행하지 않은 검증은 결과처럼 쓰지 않는다. 본문을 반복하지 않고 작업 판단에 필요한 사실만 남긴다.
- **PR 생성:** [PR 템플릿](../../../.github/pull_request_template.md)에 관련 Issue 번호와 무엇을 왜 바꿨는지 적는다. Issue 연결이 없으면 먼저 확인한다.

변경 유형은 템플릿 본문에 넣지 않는다. Issue와 PR에는 [Git 규칙](../../../docs/convention/git-convention.md)에 따라 작성자가 해당 `type:*` 라벨을 정확히 하나 지정한다. 확인 방법과 결과는 Issue 템플릿 항목 대신 Issue 코멘트에 기록한다.
